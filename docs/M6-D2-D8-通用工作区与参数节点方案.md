## 1. 目标与边界

### 目标

1. 任意 ROS 2 工程（不依赖目录名、不依赖 `nav2027_ws`）都可以：
   - 选择工作区根目录；
   - 扫描 `package.xml`、launch、params/YAML、URDF 等；
   - 在 Explorer 中显示 package/launch/params 文件；
   - 支持 `colcon build`、launch、单节点启动、RViz/Gazebo 配置。
2. 参数节点：
   - 双击参数节点 → 在 VSCode 打开参数源文件和行号；
   - 编辑保存后，UI 自动刷新参数值；
   - 消费节点输入区显示所用参数；参数多时折叠、分组、搜索；
   - 运行时参数走 ROS `set_param`，源文件参数默认只读，不在 UI 内直接改 YAML。

### 不在本方案内

- 不自研 Monaco/CodeMirror 代码编辑器（D5）；
- 不做 Game 视图；
- 不自动修改用户的 ROS 工程源文件；
- 不在默认 e2e 中真编译/真启动 ROSWORK；
- 不要求 ROS 1；首版只承诺 ROS 2（发现 ROS 1 工程时给诊断，不崩溃）。

## 2. D2：通用 ROS 工作区

### 2.1 产品形态

保留当前 Web UI 与 Rete 画布，外面加一个轻量桌面壳（Tauri 优先，Electron 备选），并内置本机 `rosui-agent`：

```text
Desktop Shell (Tauri/Electron)
  └─ Browser (Vite/React)
      ├─ Explorer / EditorTabs / Inspector / BottomPanel
      ├─ WorkspaceClient  ── HTTP/WebSocket 127.0.0.1:8787
      └─ RosClient        ── rosbridge :9090（已有）

rosui-agent (随桌面壳启动)
  ├─ workspace scanner（package.xml / launch / yaml）
  ├─ project importer/exporter（.rosui / ROS 工作区）
  ├─ file watcher（参数文件变化）
  ├─ VSCode launcher（code -g file:line:col）
  ├─ colcon/launch/process manager（白名单模板）
  └─ ROS 环境探测（不硬编码 distro/path）
```

为什么需要桌面壳 + agent：

- 纯浏览器不能读取任意本地目录，也不能可靠地打开原生目录选择器；
- 纯浏览器不能 `colcon build`、不能启动 ROS launch、不能可靠地 `code -g`；
- 现有 `RosClient` 只能连 rosbridge，不能做文件系统和进程操作。

所以不是“不能打开/编辑 ROS 工程”，而是要把通用软件做成桌面应用；Web 版本仍可作为只读查看器。桌面壳负责窗口、原生文件选择、生命周期；agent 负责文件系统、VSCode、colcon、ROS 进程。

### 2.2 打开工作区流程

1. 用户点 `Open Workspace`。
2. 桌面壳使用原生目录选择器；Web fallback 用路径输入 + 最近工作区列表。
3. 选择后创建 `WorkspaceSession`，UI 和 agent 契约不变；桌面壳只负责窗口/文件选择/生命周期。
4. agent 校验：
   - 路径存在、是目录、在允许的 root 白名单内；
   - 不要求目录名含 `ws`、不要求固定层级；
   - 允许用户显式确认后扫描任意本机目录。
5. agent 扫描并返回 `WorkspaceSnapshot`，UI 建 Explorer 树。
6. 最近工作区只记录路径和轻量元数据；不把整个文件树塞进 GraphIR。

### 2.3 通用扫描规则

不假设 workspace 布局，按以下优先级：

1. 若目录有 `src/`，扫描 `src/**/package.xml`；
2. 若根目录自身有 `package.xml`，作为单包/overlay 处理；
3. 递归查找 `package.xml`，限制深度与忽略目录：
   - 忽略 `.git`、`build`、`install`、`log`、`node_modules`、`.rosui`；
4. 解析 `package.xml`：
   - `name`、`version`、`exec_depend`、`build_type`；
   - 标记 `COLCON_IGNORE` 包；
5. 查找：
   - `launch/**/*.launch.py`、`*.launch.xml`、`*.launch.yaml`；
   - `params/**/*.yaml`、`config/**/*.yaml`、包内 `*.yaml`；
   - 可选 `urdf/xacro`；
6. 若存在 `install/setup.bash` 或多个 overlay，标记为 build/run 候选；
7. 用 `colcon list --base-paths <root>` 做交叉校验（agent 环境里可用才调用）；
8. 返回每个 package 的相对路径、包名、launch/params 列表；不返回绝对路径给浏览器之外的地方。

### 2.4 工作区数据模型（sidecar）

不要把 workspace/package/launch/topic/QoS 塞进 GraphIR v1（`.strict()` 会拒绝未知字段）。新增独立 sidecar：

```ts
interface WorkspaceConfig {
  version: 1;
  roots: string[];
  activeRoot: string | null;
  recent: Array<{ path: string; name: string; lastOpenedAt: string }>;
  ui?: {
    openTabs: string[];
    activeTab: string;
    dockSizes: Record<string, number>;
  };
}

interface WorkspaceSnapshot {
  root: string;
  packages: PackageInfo[];
  launchFiles: SourceFileInfo[];
  parameterFiles: SourceFileInfo[];
  diagnostics: Diagnostic[];
}

interface PackageInfo {
  name: string;
  relativePath: string;
  buildType?: string;
  launchFiles: SourceFileInfo[];
  parameterFiles: SourceFileInfo[];
}

interface SourceFileInfo {
  id: string;              // hash(path)，跨重启稳定
  relativePath: string;
  kind: 'launch' | 'yaml' | 'xml';
  size: number;
  modifiedAt: string;
}
```

落盘策略：

- 默认写应用数据目录（例如 `~/.config/rosui/workspaces.json`），不碰 ROS 工程；
- 用户显式选择“随工作区保存”时，才写 `<workspace>/.rosui/workspace.json`；
- 写前备份 `workspace.json.bak-<timestamp>`（D7）；
- 烟测/编译路径永远不写 ROSWORK（D9）。

### 2.5 Explorer UI

- 根节点：最近工作区；当前 root 高亮；
- 包节点：图标 + 包名 + 路径；
- 文件节点：launch / yaml / package.xml；
- 顶部：`Open Workspace`、刷新、搜索、过滤；
- 双击文件：打开 EditorTab（只读文本预览或“在 VSCode 打开”）；
- 不把固定 3 条路径硬编码进组件；Phase 2 删除现有静态 Explorer 数据。

## 2A. ROSUI 工程模式：把任意 ROS 仓库变成可编辑工程（v2 新增）

### 2A.1 为什么需要工程模式

直开模式适合“我就在这台机器上改现有仓库”。工程模式适合用户提出的另一条路径：把 2027 仓库完整收进一个 `.rosui` 工程，像 Unity/剪辑软件工程一样打开、编辑、另存，再导出一个**完整、可编译的 ROS 工作区**，原仓库保持不变。

工程模式不是把 GraphIR 当源码仓库，而是：

- `sources/`：ROS 仓库的完整源码副本（去掉 `build/install/log/.git` 等构建产物）；
- `graph.json`：画布/节点/连线/参数绑定；
- `project.json`：工程元数据、ROS 发行版、导入来源、默认 launch、导出设置；
- `assets/`：地图、URDF、world、模型等非源码资源（可配置是否复制）；
- `backups/`：每次写回前的文件备份；
- `export-manifest.json`：上次导出的文件清单、哈希、构建结果。

`.rosui` 是**目录**（便于外部 VSCode 直接编辑、便于 diff/备份）；后续可增加单文件 `.rosuiproj`（zip 打包）作为分发格式，内部仍是同一结构。

### 2A.2 导入流程

1. 桌面壳原生目录选择器选择任意 ROS 工作区根目录（不限定 `/home/ddyyxx/ROSWORK`）。
2. agent 扫描 `src/**/package.xml`、`launch/*.py|*.xml|*.yaml`、`params/*.yaml`、`config/*.yaml`、`urdf/`、`worlds/`、`maps/`，生成 package/launch/param 索引。
3. 默认 **copy 模式**：把 `src/`、必要的 `config/`、`assets/` 复制到工程 `sources/`；排除 `build/`、`install/`、`log/`、`.git/`。原仓库只读，不修改。
4. 生成初始图：
   - 每个 package 一个可折叠 package 节点；
   - `startup.launch.py` 启用的 launch 生成 launch/driver/topic/param 节点；
   - 注释掉的 launch 显示为灰色“未启用”；
   - YAML 参数按 group/key 生成参数节点；
   - 话题节点在连接 ROS 后补发布者/订阅者/QoS；未连接时用静态 launch/源码线索。
5. 生成 `project.json`、`graph.json`，并记录每个节点的 source ref（文件相对路径 + 行号/键路径）。

2027 仓库建议导入为：

```text
~/ROSProjects/nav2027.rosui/
  project.json
  graph.json
  sources/                  # 从 /home/ddyyxx/ROSWORK/nav2027_ws 复制
  assets/                   # 地图/URDF/world 等
  backups/
```

默认不复制 `ros_deps/`，先使用本机已安装的依赖；如果导出需要自包含，可在导入向导勾选“把 vendor/ros_deps 一并纳入工程”。原 `/home/ddyyxx/ROSWORK` 不动。

### 2A.3 编辑流程

- **源码编辑**：Explorer 右键文件 / 节点上的“打开源文件” → 本机 agent 执行 `code -g <工程内绝对路径>:<line>`，VSCode 直接打开 `sources/` 副本。保存后 agent 用文件 watcher 通知 UI 刷新对应节点。
- **参数节点编辑**：参数组节点和单参数节点的值都可以在节点内直接编辑；提交时 agent 按 `ParamSourceRef` 写回对应 YAML 文件（先备份、保留注释/缩进、只改目标 key），再刷新源索引。双击 / “在 VSCode 打开”仍可跳转源文件行，适合大改或看上下文；运行中的 ROS 参数另走 `rosapi/set_param`，不回写 YAML。
- **图编辑**：拖节点、连线、折叠/展开参数组；GraphIR 只存图结构与参数引用，不把整个源码仓库塞进 JSON。
- **代码补全/AI**：完全交给 VSCode/Copilot/Cline；ROSUI 只保留“打开指定文件/行”和可选的 AI 工具调用接口，不内置 Monaco/CodeMirror。

### 2A.4 导出流程

1. 用户选择导出目录（必须是新目录；禁止直接覆盖原 ROS 仓库）。
2. 复制工程 `sources/` 到导出根目录；保留 `src/`、`package.xml`、`CMakeLists.txt`、launch、yaml、urdf、map 等；不导出 `build/install/log`。
3. 把图上的参数修改写回导出的 YAML/launch 副本；生成 `export-manifest.json`（文件清单、哈希、跳过项、警告）。
4. 在**导出目录或临时 build/install/log** 运行 `colcon build`（用户可勾选“导出后验证编译”）；不修改原仓库，不使用原仓库的 build/install 目录。
5. 构建失败时保留导出目录和日志，给出 package/文件/错误摘要，不把失败伪装成成功。

导出结果就是普通 ROS 2 工作区，可直接 `source install/setup.bash`、`ros2 launch`，不依赖 ROSUI 才能运行。`project.json`/`graph.json` 不进入导出源码，除非用户显式勾选附带工程文件。

### 2A.5 工程模式与直开模式的边界

| 能力 | 直开模式 | ROSUI 工程模式 |
|---|---|---|
| 打开任意 ROS 工作区 | 是（原地） | 是（导入副本） |
| 修改原仓库 | 是（用户明确保存时） | 否（只改工程副本） |
| 导出完整可编译仓库 | 可选 | 是 |
| 适合 2027 仓库 | 可以 | **推荐** |
| 依赖 `sources/` 副本 | 否 | 是 |
| 备份/回滚 | 文件级备份 | `backups/` + manifest |

### 2A.6 2027 仓库验收

- 导入 `/home/ddyyxx/ROSWORK/nav2027_ws`，生成 `.rosui` 工程后原目录 mtime/内容不变。
- 工程 Explorer 能列出 24 个 package；`startup.launch.py` 的启用/注释节点正确呈现；参数节点能定位到 `global_config.yaml`/`params.yaml` 行号。
- 双击参数节点能用 VSCode 打开工程内 `sources/` 文件。
- 不改代码直接导出到临时目录，`colcon build` 至少达到与原仓库相同的构建结果；再验证一次参数节点修改后导出仍可编译。
- 若 2027 依赖 `ros_deps`，导出验证使用本机已安装依赖；需要自包含时分阶段支持 vendor。

## 3. D8：参数节点与 VSCode 编辑

### 3.1 参数来源分类

必须区分两类，不混在一起：

| 类型 | 来源 | UI 行为 |
|---|---|---|
| 源文件参数 | YAML/launch 的 `ros__parameters` | 节点内可编辑，提交自动写回对应 YAML（先备份、保留格式）；也可双击在 VSCode 打开源文件行；保存后 watcher 刷新 |
| 运行时参数 | 已连接 ROS 节点的 parameter server | 可在 UI 改值，走 `set_param`；显示当前值/类型/是否成功 |

首版以“源文件参数节点”为主；运行时参数仍复用现有 `useParamBinding`。

### 3.2 参数源索引

agent 解析 YAML/launch 后返回：

```ts
interface ParamSourceRef {
  sourceId: string;
  filePath: string;       // agent 内部绝对路径，不回传浏览器敏感内容
  relativePath: string;
  line: number;
  column?: number;
  keyPath: string;        // 如 /controller_server.ros__parameters.follow_path
  group?: string;         // YAML 节点/命名空间
  name: string;
  valueType: ParamValueType;
  value: unknown;
  editableInVscode: boolean;
}
```

要求：

- 行号必须精确到参数键；不能只给文件；
- YAML 解析保留 key 路径；launch 参数（`DeclareLaunchArgument`/`ParameterValue`）单独标记；
- 文件变化后重新解析并产生稳定的 `sourceId`/`keyPath` 映射；
- 解析失败给 Diagnostics，不静默丢弃。

### 3.3 参数节点类型

建议同时提供两个节点，避免“每个参数一个节点”把画布撑爆：

1. **ParamValueNode（单值参数节点）**
   - 一个参数；
   - 显示名称、值、类型、来源文件名；
   - 节点内可直接编辑；提交时写回该参数在 YAML 中的 key，先备份并保留注释/缩进；
   - 输出端口 `value`；
   - 双击 / “在 VSCode 打开”跳转源文件行，适合大改/看上下文；
   - 适合少量关键参数、单节点输入参数。

2. **ParamGroupNode（参数组/参数总线节点）**
   - 一个 YAML 文件/一个 ROS 节点参数组；
   - 输出一个 `param-bus`（一个 bundle，不铺 N 条边）；
   - 节点内显示参数数量；
   - 可展开后逐项编辑组内参数，提交时统一写回该 YAML，先备份并尽量保留原格式；
   - 双击 / “在 VSCode 打开”跳转该组首个参数行；
   - 参数多时默认折叠，只显示计数；消费节点的输入区按组折叠/搜索。

3. **消费节点的 params 输入区**
   - 节点增加一个可选 `params` 输入端口（`param-bus`）；
   - `ParamGroupNode` 连到消费节点后，消费节点输入区显示“使用参数”列表；
   - 每条显示：参数名、当前值、来源文件/行；
   - 点击条目 → VSCode 打开；
   - 超过 6 条折叠为 `+N 更多`，支持搜索/按文件分组；参考 Unity Inspector 的折叠块，而不是无限长列表；
   - 参数列表是**节点 UI 的一部分**，不是单独的全局侧栏；右侧 Inspector 只显示选中节点的详情。

### 3.4 双击参数节点 → VSCode；节点内编辑自动写回

流程：

1. 双击 `ParamValueNode`/`ParamGroupNode`；
2. UI 从 sidecar 取 `ParamSourceRef`；
3. 调 agent `POST /vscode/open`：
   ```json
   { "path": "/abs/workspace/src/.../params.yaml", "line": 42, "column": 3 }
   ```
4. agent 校验路径在当前 workspace 内，执行 `code -g <path>:<line>:<column>`；
5. 若 `code` 不存在：回退 `code-insiders`、`codium`，再回退展示可复制命令；
6. 不把 VSCode 嵌入网页，也不做自由文本 YAML 编辑器；参数值用节点内类型化控件编辑，写回由 agent 负责（D5）。

节点内编辑的写回规则：

- 只改 `ParamSourceRef.keyPath` 指向的 key，尽量保留注释、缩进、锚点和同文件其他内容；
- 写前备份到工程 `backups/`（直开模式写应用数据备份目录），使用临时文件 + 原子 rename；
- 写回失败时原文件不变，并在节点上显示错误/Diagnostics；
- 自己写回触发 watcher 时用 origin token 抑制回声，不重复刷新/写回；
- 多个节点同时改同一 YAML 时串行写队列；检测到外部 VSCode 已改动则提示 diff/重新加载，不能静默覆盖。

文件保存后：

1. agent 用 `fs.watch`/去抖（200-300ms）监听参数文件；
2. 重新解析受影响 source；
3. 通过 WebSocket/SSE 推送 `param-source-changed`；
4. UI 更新参数节点和消费节点的参数列表；
5. 只有值变化才更新；不自动改 GraphIR 历史栈（避免 VSCode 每次保存生成 undo 边界）。

### 3.5 参数节点与 GraphIR v1

尽量不升 GraphIR schema：

- 新增节点 `NodeIR.type`：`param-value`、`param-group`；
- `NodeIR.params` 继续用现有 `ParamBinding` 结构存参数值/类型/本地 key；
- `ParamBinding.node` 使用稳定 source 标识（如 `@source:<sourceId>`），`ParamBinding.param` 使用 keyPath；
- `sourceId → {relativePath,line,column,group}` 存 sidecar，不进 GraphIR；
- 消费节点通过 `ParamGroupNode` 的 `param-bus` 输出连接，不新增 GraphIR 字段；
- 旧图加载不受影响；未知节点类型按现有逻辑诊断/跳过，不崩溃。

如果实现中发现 `ParamBinding` 语义不够，再评估 GraphIR v1.1（最小可选字段），不要现在大改 schema。

## 4. Agent API（本机 127.0.0.1）

必须绑定 `127.0.0.1`，带本地 token，禁止任意 shell。建议最小 API：

```text
POST /workspace/open          { path } -> WorkspaceSnapshot
POST /workspace/scan          { root } -> WorkspaceSnapshot
GET  /workspace/recent
POST /workspace/save-config   { root, config } -> { backupPath }
POST /vscode/open             { path, line, column } -> { command }
GET  /events                  (SSE/WS: scan-progress, file-changed, process-log)
POST /build                   { root, packages?, buildBase?, installBase? }
POST /launch                  { root, package, launchFile, args, visualizer }
POST /node/start              { root, package, executable, args }
POST /process/stop            { id }
GET  /diagnostics             { root }
```

安全：

- `root` 必须先通过用户显式打开并存入白名单；
- 所有 `path` 必须 `realpath` 后仍在白名单 root 内；
- 命令只接受固定模板，不接受任意 shell 字符串；
- `vscode/open` 只允许 `code/code-insiders/codium -g`；
- 编译/启动默认写到临时目录或用户指定目录；
- 不静默写 `/home/ddyyxx/ROSWORK`；
- 日志/进程组按现有 `DetachedGroup` 思路回收；
- agent 端口仅本机，默认要求 token；不把 token 写进源码/聊天。

## 5. 交付阶段

### Phase 2A：桌面壳 + 通用工作区骨架

- Tauri 桌面壳（原生目录选择） + agent 最小服务 + `Open Workspace` + 扫描器；

- 直开模式 sidecar 默认只存在应用数据目录；
- 测试用 fixture workspace，不依赖 ROSWORK。

### Phase 2A2：ROSUI 工程模式

- 工程管理器：新建/打开 `*.rosui` 目录；
- 导入任意 ROS 工作区为 `sources/` 副本，排除 `build/install/log/.git`；
- 生成 `project.json`、`graph.json`、`export-manifest.json`；
- 导出到新目录并保留完整 ROS 包结构；参数节点修改写回导出副本；
- 2027 仓库按 `nav2027.rosui` 导入，先做 copy 模式；`ros_deps` 默认外置、可选 vendor；
- 导出后可选临时目录 `colcon build` 验证，绝不改原仓库。

### Phase 2B：参数源索引 + 参数节点

- YAML/launch 解析 + `ParamSourceRef`；
- `ParamValueNode` / `ParamGroupNode`；
- 参数组/单参数节点内编辑 + 自动写回对应 YAML（备份、格式保留、原子替换）；
- 消费节点 `params` 输入区，折叠/搜索/分组；
- 双击 VSCode（agent stub + 真 `code` opt-in）；
- 文件 watcher 回灌；YAML 回写后重新解析以确认行号/keyPath 未漂移。

### Phase 2C：真实 ROS 工程只读试运行

- 用任意用户选择的 ROS 工程做只读扫描/展示；
- 不在默认测试中编译/启动；
- 诊断 package/launch/params 缺失、重复、冲突。

### Phase 2D：编译/launch/单节点/RViz/Gazebo

- 接 agent 模板命令；
- Gazebo 只做 world 导入/诊断，不假设已安装；
- RViz 沿用 launch 内置，避免重复启动；
- 每节点启动按钮 + 进程日志；
- 真机执行 opt-in，用户确认后运行。
