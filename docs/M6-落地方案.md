## 0. 硬约束（写进每个 Phase 的 Definition of Done）

2. **类型与测试基线**
   - TS `strict`，**禁 `any` / `@ts-ignore`**（需要时用 `unknown` + 收窄）；不新增未经 lead 批准的 npm / Python 重依赖。

4. **本机 agent 安全边界**
   - 只监听 `127.0.0.1`；本地 token 鉴权（不写仓库 / 聊天）；仅白名单根目录（默认 `/home/ddyyxx/ROSWORK`，可扩但只允许 `/` 盘）。

   - 进程用 detached process group + `/proc/<pid>/stat` starttime 校验整组回收（延续 T-033/T-032 的 rosbridge 回收经验）；**默认 dry-run**，真编译 / 真启动必须显式 UI 确认，且不进默认 e2e。
   - `ros2` 相关命令一律先 `source /opt/ros/jazzy/setup.bash`，再按 workspace source 对应 setup（`/home/ddyyxx/ROSWORK/setup_nav2027.sh` 或 `adaptive_lio_ws` 对应脚本）。
5. **产品边界**
   - **不做 Game 视图**；Unity 只参考多面板 / Inspector / 节点与代码编辑 / Console / 顶部 Run；VSCode 只参考工作区 / 文件树 / 多标签 / 命令面板 / 状态栏。
   - 首版代码编辑优先“轻量 textarea + 行号 + Tab + 只读预览”，是否引入 Monaco / CodeMirror 6 列为开放问题（见 §8）。
   - 审查闭环：每个 Phase 都走“实现方自检 → 独立 reviewer（UI/产品/ROS/安全四视角）→ 修 P0/P1 → re-review → 全量门禁 → 开/更新 PR”。

## 2. 分支策略：从哪切、如何链式 PR、如何不碰 #3–#6 的 base

### 2.1 现状与事实

- 分支链：`main ← #3 (feat/m5-save-load?) ← #4 (feat/m5-lod?) ← #5 (feat/m5-toast-acceptance?) ← #6 feat/m5-undo-copy-paste`，均未合入 main；#6 的直接 base 是 `feat/m5-toast-acceptance`。
- 因此 M6 **不能从 main 切**（会丢掉 #3–#6 的实现），也**不能把 M6 的 commit 直接推到 #3–#6 任一分支**（会改变它们的 base 内容与 review 范围）。

### 2.2 推荐方案：从 #6 head 切 M6 长分支 + M6 内部链式 PR（stacked PR）

```
main
 └─ #3 ─ #4 ─ #5 ─ #6  (feat/m5-undo-copy-paste, 当前最末端)
        └─ feat/m6-phase1-shell        (base: feat/m5-undo-copy-paste)
             └─ feat/m6-phase2-agent    (base: feat/m6-phase1-shell)
                  └─ feat/m6-phase3-nodes (base: feat/m6-phase2-agent)
                       └─ feat/m6-phase4-run (base: feat/m6-phase3-nodes)
                            └─ feat/m6-phase5-review (base: feat/m6-phase4-run)
```

规则：

1. **M6 第一分支从 `feat/m5-undo-copy-paste` 的 head 切**（若用户在开工前已按顺序合入 #3–#6，则改从更新后的 `main` 切；二选一由 lead 在 G0 拍板，见 §8 决策 D1）。
2. 每个 Phase 一个分支，PR 的 base 显式设为上一个 M6 Phase 分支；**绝不 retarget / rebase 到 #3–#6 的任何分支**，不修改它们的 base 分支名与提交历史。
3. **每个 Phase PR 的生命周期**：实现方自检（build/check/vitest/focused e2e）→ 建 PR（草稿）→ reviewer 四视角 → 修 P0/P1 → re-review → 全量门禁 → 标 ready → lead  squash/merge 到 M6 链下一层。**未经当前对话明确授权不 push 任何分支**。
4. 若 #3–#6 在 M6 进行中被合入 main：只让 M6 链的最顶层按正常流程 rebase 到新 main（由 lead 单独决定），仍不直接改 #3–#6 的历史；rebase 后重跑全量门禁。
5. 文档 / 任务板：`docs/reviews/M6-P<n>-review.md`、`docs/reviews/M6-P<n>-acceptance.md` 随对应 Phase PR 更新；`docs/backlog.md` 不在本方案任务中修改（实际实施阶段由 lead 另开卡）。

## 4. 数据模型：sidecar schema 与 agent API 契约

### 4.1 不进 GraphIR 的边界

- `.rosui.json`（GraphIR v1）仍只含 `{ version: 1, nodes, edges }`，`parseGraph().strict()` 不变。
- 新增三类 sidecar（**独立于 `.rosui.json`**，建议放工作区局部 `.rosui/` 下或 UI session 存储；实际落盘路径由 lead 在 G0 拍板，见 §8 D5）：
  - `.rosui.workspace.json`：工作区根 / tabs / visualizer 选择 / launch target / recent。
  - `.rosui.index.json`：扫描缓存（packages / launch / params / drivers / topics / diagnostics）。
  - 运行时内存：topic graph、QoS、进程状态、日志尾（默认不落盘）。

### 4.2 sidecar TypeScript 形状（放在 `apps/web/src/workspace/types.ts`，由 agent 序列化对齐）

```ts

export type LaunchInfo = {

};
export type ParamInfo = {

  value: unknown; defaultValue?: unknown;

};
export type QosInfo = {
  reliability: 'reliable'|'best_effort'|'system_default'|'unknown';

  source: 'static'|'runtime'|'unknown';
};
export type EndpointInfo = {
  node: string; namespace?: string; gid?: string;

export type TopicInfo = {
  name: string; type: string;

  compatibility: 'ok'|'warn'|'unknown'; warning?: string;
};
export type ProcessHandle = {
  id: string; label: string; command: readonly string[]; cwd: string;
  state: 'starting'|'running'|'exited'|'failed';
  pid?: number; starttime?: number; pgid?: number;    // /proc/<pid>/stat starttime 防复用

};
export type Diagnostic = {
  id: string; severity: 'error'|'warning'|'info';
  message: string; file?: string; line?: number; hint?: string;
};
export type UiSessionState = {
  workspaceIds: readonly string[];
  activeTabs: readonly { kind: 'graph'|'code'|'topic'|'log'; ref: string }[];
  visualizer: 'rviz'|'gazebo'|'none';
  launchTarget?: string;
  selectedNodeId?: string;
};
```

## 5. 参数 / 驱动 / 话题三类小节点的复用方式（不污染初始 5 节点）

### 5.1 复用 `NODE_REGISTRY` 与 `nodeRenderers`

- `NODE_REGISTRY`（`apps/web/src/rete/nodes.ts:280`）现有 gain/threshold/label/mode/switch/pose/inspector/script。三类小节点通过**同一 `NodeSpec` 形状**扩展，新增条目建议：

```ts
// 仅示意；实际定义放 Phase 3
workspaceParam: { type:'WorkspaceParam', label:'参数', inputKey:'value', inputLabel:'值',
                  widget:'json', valueType:'string', initial:'', workspaceOnly:true },
workspaceDriver:{ type:'WorkspaceDriver', label:'驱动', inputKey:'status', inputLabel:'状态',
                  widget:'text', valueType:'string', initial:'unknown', workspaceOnly:true },
workspaceTopic: { type:'WorkspaceTopic', label:'话题', inputKey:'flow', inputLabel:'信息流',
                  widget:'text', valueType:'string', initial:'', workspaceOnly:true },
```

- `workspaceOnly: true` 的条目**不得进入默认建图路径**：`createNode()` / `kindForType()` / `serializeGraph()` 照常支持（保持 `serialize.test.ts` 的“覆盖 NODE_REGISTRY 全部条目”测试成立），但工具栏 `+ Gain/Pose/Inspector/Script` 与初始 5 节点（Gain/Threshold/Label/Mode/Switch）不注册它们；只有工作区 Explorer 勾选包 / Topic Tab 打开时才动态 `addNode()`。
- 渲染复用 `nodeRenderers.tsx` 的 `classicNodeRenderer` + `withNodeLod`；InspectorNodeComponent / ScriptNodeComponent 的自定义外壳作为参照，新节点外壳统一带 `data-node-kind="WorkspaceParam|WorkspaceDriver|WorkspaceTopic"`，不改 `data-testid="node"` 的既有语义。
- 参数编辑复用 `apps/web/src/controls/model.ts` 的 `RosuiControl` 与 `react.tsx` 控件族（number/text/boolean/select/pose/json），通过 `binding/controlAdapter.ts` 把 sidecar 的 `ParamInfo` 适配成现有 `ParamBinding`（`node/param/valueType/mode/widget/value/constraints`），从而复用 `useParamBinding` 的双向同步与回声抑制（2s 同值吞回声、300ms 首帧丢弃、失败回滚 + toast）。
- `ParamBrowser.tsx` 与 ParameterNode 共用同一数据源 hook（建议 `workspace/useParamTree.ts`），避免两套刷新逻辑；runtime 绑定仍走 `getSharedClient()`，权限/断线行为与 M2/M4 一致（断线不锁控件，只停下发）。
- 驱动节点只显示身份与状态（包名、可执行、launch 引用、pid、日志 tab），启动按钮走 §4.3 的模板 API；不把驱动伪装成可连线的 ROS 参数端口。
- 话题节点在独立 Topic Tab 中以话题为中心，pub/sub 端点为周围卡片；QoS 四元组从 `QosInfo` 渲染徽标；边动画 / `hz` 数字表示信息流；兼容警告由 agent 计算 `compatibility` 字段，前端只展示，不自行猜 DDS 规则。

### 5.2 LOD `TYPE_SIZES` 注意点

- `apps/web/src/rete/LodNode.tsx:30` 的 `TYPE_SIZES` 目前按实测写死：Gain/Threshold/Label/Mode/Switch 180×119、Pose 180×144、Inspector 180×71、Script 252×273，`FALLBACK_SIZE` 180×119。
- 三类小节点若被渲染到画布，必须在 Phase 3 用一次性探针实测 full 尺寸后写入 `TYPE_SIZES`（键为 `WorkspaceParam` / `WorkspaceDriver` / `WorkspaceTopic`），**不能只靠 fallback**：否则 k<0.32 切占位再放大时节点会跳尺寸，破坏 M5 的“socket 中心偏移 ≤2px”断言。
- 占位节点复用 classic 布局类与 `data-testid="node-lod"`，不卸载 NodeView；选中态仍由 `nodepicked` → DOM `data-selected` 同步，不用 `node.selected`。
- 大 workspace 扫描时默认折叠 / 延迟挂载新节点；禁止在自动 commit 中 `setGraph()`（M5 perf 结论）；`CurrentIR`（`data-testid="current-ir"`）不在扫描期间刷新。

### 5.3 不污染初始 5 节点画布的硬检查

- e2e 断言初始 `current-ir` 节点数 = 5 且 type 集合 = {Gain, Threshold, Label, Mode, Switch}；新增节点只能通过显式用户动作（勾选包 / 打开 Topic Tab / DEV 钩子）出现。
- `e2e/perf.spec.ts` 的 200 节点混合图节点种类不变（不混入 workspace 节点），保证 745.5ms / 326.8ms 可比。

## 6. 一键编译运行、可视化选择、每节点启动与 ROSWORK 7 问题面板

### 6.1 一键流程与命令模板（全部先 `source /opt/ros/jazzy/setup.bash`）

```
选 workspace → 选 launch target（默认 bringup/startup.launch.py）→ 选 visualizer（rviz|gazebo|none）
→ [可选] build → source workspace setup → launch → attach logs → 打开 Topic Graph
```

- **Build 模板**（仅由 agent 构造，参数来自扫描结果）：
  ```bash
  source /opt/ros/jazzy/setup.bash
  source /home/ddyyxx/ROSWORK/setup_nav2027.sh
  cd /home/ddyyxx/ROSWORK/nav2027_ws
  colcon build --symlink-install --packages-select <pkg...> --event-handlers console_direct+
  ```
  不执行 `rosdep install`；缺失依赖进 Problem 面板（ROSWORK README 已说明 rosdep 未初始化，依赖靠 `ros_deps/root` 手工解包）。
- **Launch / 节点模板**：`ros2 launch bringup startup.launch.py self_color:=red use_fake_referee:=false ...`；单节点 `ros2 run <pkg> <exe> --ros-args -p <name>:=<value>`；参数值来自 sidecar / 用户表单枚举，UI 不拼 shell 字符串。
- **Visualizer 模板**：
  - `rviz`：`rviz2 -d <config>`，默认选项为**沿用 launch 内置 RViz**（startup.launch.py 已按 `self_color` 条件启动 rviz2），另开自定义 RViz 需显式选择配置路径。
  - `gazebo`：先探测 `gz` / `gazebo` 与 world 文件；缺失报 `CMD_MISSING` / 无 world 提示，绝不假装成功；当前 ROSWORK 未发现 Gazebo 入口（见问题 7）。
  - `none`：不拉可视化。
- **Dry-run 默认**：所有 start/build/visualizer API 未带 `confirmToken` 时只返回“将执行：argv + cwd + env 差异”，不改系统状态；真执行必须 UI 显式确认并生成一次性 `confirmToken`。

### 6.2 安全边界（不可协商）

1. root 白名单 + 固定 `templateId`；禁止任意命令字符串 API。
2. 参数校验：拒绝 `; && | $()` 反引号、换行、`>` `<`、绝对路径逃逸白名单；枚举项用白名单表。
3. 进程：`subprocess.Popen(..., start_new_session=True, cwd=allowedRoot)`；记录 pid / starttime / pgid；停止时 `os.killpg()` 并比对 `/proc/<pid>/stat` 第 22 字段 starttime，防止 PID 复用误杀。
4. 不走 sudo；不写 ROSWORK 源文件（包括“在 launch 中启用”入口只生成建议 diff，不落盘，除非用户单独授权写文件）。
5. 端口：agent 仅 127.0.0.1；5180/9090 e2e 串行；真执行用例 opt-in 且不在默认 e2e。
